# Webhook Gateway — Project Brief

## Что строим

Webhook Gateway — сервис-посредник между внешними источниками событий и внутренними получателями.
Он принимает подписанные HTTP-вебхуки, надёжно сохраняет каждое событие, доставляет его подписчику
с повторами при сбоях и даёт посмотреть историю и переотправить любое событие.

Проблема, которую решаем: внешний сервис шлёт вебхук один раз и не ждёт. Если получатель в этот
момент недоступен или упал, событие теряется. Gateway берёт приём на себя за миллисекунды, а доставку
выполняет асинхронно и столько раз, сколько нужно.

## Для кого

- **Отправитель** — внешний сервис (платёжка, CRM, CI и т. п.), который шлёт вебхуки.
- **Получатель (подписчик)** — внутренний сервис, которому нужны эти события.
- **Оператор** — разработчик, который настраивает подписчиков, смотрит логи и делает replay.

## Критерии успеха MVP

Каждый критерий доказывается автоматическим тестом. Шаг, который его закрывает, указан справа.

| # | Критерий | Как проверяем | Шаг |
| --- | --- | --- | --- |
| 1 | События не теряются, если получатель, Redis или воркер временно недоступны | Integration + E2E: получатель отдаёт 500 → после восстановления событие `delivered`; Redis остановлен в момент приёма → событие доставлено после старта Redis | 12, 14, 18 |
| 2 | Повторная отправка того же вебхука не создаёт дублей; получатель может отсечь повторную доставку по `X-Webhook-Id` | Integration: 3 одновременных запроса с одним ключом → 1 строка; каждая исходящая доставка несёт `X-Webhook-Id` | 8, 11, 18 |
| 3 | Всё поднимается одной командой `docker compose up --build` | E2E поверх поднятого compose | 1, 10, 18 |
| 4 | Историю любого события можно посмотреть и переотправить через API | Integration: `GET /events/:id/attempts`, `dead` → replay → `delivered` | 15, 16, 18 |

## Глоссарий

- **Эндпоинт (endpoint)** — зарегистрированный подписчик: куда доставлять (`target_url`) и чем подписывать исходящие запросы (`signing_secret`).
- **Событие (event)** — один принятый входящий вебхук. Хранится в PostgreSQL; это источник истины.
- **Ключ идемпотентности** — заголовок `Idempotency-Key` или SHA-256 сырого тела; уникален в пределах эндпоинта.
- **Попытка (delivery attempt)** — одна HTTP-отправка события подписчику с результатом.
- **Статусы события** — `pending` → `processing` → `delivered` | `failed` (неповторяемая ошибка) | `dead` (попытки исчерпаны).
- **DLQ (Dead Letter Queue)** — очередь `webhook-dlq` для событий в статусе `dead`; нужна для наблюдения и алертов.
- **Replay** — ручная переотправка события оператором.

## Архитектура (кратко)

```
Отправитель ──HTTP──► app (Fastify) ──INSERT──► PostgreSQL (источник истины)
                          │
                          └──enqueue(eventId)──► Redis / BullMQ ──► worker ──HTTP──► Получатель
                                                                      │
                                                                      └──► delivery_attempts, статус события
```

- `app` — приём вебхуков, admin-API, Logs API, replay.
- `worker` — доставка, повторы, DLQ, восстановление «застрявших» событий.
- Общий код у них только `config`, `db`, `queue`.

## За рамками MVP

Веб-интерфейс дашборда; мультитенантность и пользовательская авторизация; секреты входящей подписи
на каждого отправителя; ротация секретов; fan-out одного события на несколько подписчиков;
трансформации payload; метрики Prometheus; CI-пайплайн; очистка старых событий (retention).
